# Abnahme eines Releasekandidaten

Diese Vorlage kopieren und nur beobachtete Ergebnisse eintragen. Leere Felder
und offene Punkte bedeuten keine Freigabe. Den ausgefüllten Beleg am Release
ablegen oder in einem späteren Dokumentationscommit unter `docs/releases/`.

- Produkt / Version / Tag:
- Vollständiger Quellcommit:
- CI-Lauf-URL und verwendete Python-Version:
- Datum / prüfende Person:
- Artefaktnamen und SHA-256 (einschließlich Source-ZIP):
- Windows / genaue Bedrock-Version / Hardware / Treiber:
- Welt / Seed / Grafikprofil / aktivierte Pakete:

| Prüfung | Ergebnis (offen / bestanden / fehlgeschlagen) | Beleg / Beobachtung |
|---|---|---|
| Automatische Tests, Versionen und Generatordrift | offen | |
| Vollständiger Wiederholungsbuild und Prüfsummen | offen | |
| Source-ZIP-Inhalt und eigenständiger Build | offen | |
| Neuimport sowie Update von der vorherigen Version | offen | |
| Content-Log nach Import, Laden und Spielen | offen | |
| WQHD: beide Varianten einzeln, alle vier Stile, Stilrückwechsel | offen | |
| WQHD: Wasser/Biomwechsel, Tag/Nacht, Wetter, Himmel/Nähte | offen | |
| Leistung gemäß BENCHMARK.md, sofern Leistung behauptet wird | offen | |

Nicht anwendbare Prüfungen mit Begründung kennzeichnen. Beim ersten Release
ist der Update-von-Vorversion-Test nicht anwendbar.

- Bekannte Probleme / verbleibende Einschränkungen:
- Entscheidung: Entwurf belassen / ausdrücklich als Testversion veröffentlichen /
  stabile Veröffentlichung freigegeben:
- Freigabe durch / Datum / belegter Nutzerauftrag zur Veröffentlichung:
- Nach Veröffentlichung: URL, heruntergeladene Dateien und Prüfsummen kontrolliert:
